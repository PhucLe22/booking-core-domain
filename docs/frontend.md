# Frontend guide

For anyone working in `web/apps/` or `web/packages/`. Shared rules live in the root [CLAUDE.md](../CLAUDE.md); API rules in [api.md](api.md); tracking in [analytics.md](analytics.md).

## Stack

| Concern | Choice |
| --- | --- |
| Apps | React, TypeScript (strict), Vite, shadcn/ui |
| Server data | TanStack Query, only through Orval-generated hooks |
| Routing | TanStack Router: file-based routes, typed links and search params, loaders using TanStack Query |
| Forms | React Hook Form with two validators (below) |
| Rule previews | json-logic-js |
| Tracking, errors | PostHog and Sentry, set up by `app-kit` |
| Unit and component tests | Vitest, React Testing Library |
| End-to-end tests | Playwright |
| Component preview | Storybook (`web/storybook`), one instance for every package and app |

### Two validators, two jobs

| Form | Fields known | Validator |
| --- | --- | --- |
| Fixed forms: create site, rule editor, standard booking fields | When we write the code | Zod via `zodResolver`; schemas generated by Orval from the contract |
| Custom-field forms: a phone booth's "Floor" and "Equipment" | At runtime, defined by the tenant | Ajv via `ajvResolver`, against the JSON Schema compiled from the field definitions |

Zod can't describe fields that only exist in a tenant's configuration. Ajv validates against the same JSON Schema the backend uses, so browser and server always agree. Router search params are validated with Zod.

## Code organisation

- **pnpm workspace:** rooted at `web/`; `apps/console` and `apps/member` depend on `@booking-core/*` packages via `workspace:*`.
- **Packages from day one:** `api-client`, `ui`, `custom-fields`, `rules-editor`, `booking-ui`, `app-kit`. Anything else starts in an app and moves to a package when a second consumer needs it.
- **No imports between apps.** If both apps need something, it moves to a package.
- **Each package exports through its `index.ts`.** Nothing imports another package's internals; packages never import from `web/apps/`.
- **Inside an app:** one folder per feature under `src/features/<feature>/`, with its components, hooks and tests together.
- **shadcn/ui components** live in `web/packages/ui`, are added with its CLI, and may be edited.
- **File names are kebab-case** (`booking-card.tsx`, `use-booking-calendar-data.ts`), across packages and apps alike ([D-001](decisions.md)). `index.ts` entry points keep their name.

### Rules for packages

Packages are what products install, so they are built as libraries:

- No routing, no login screens, no global app state. React and TanStack Query are peer dependencies.
- Customise through props, not copies: labels, render functions and slots (`renderResource`, `emptyState`).
- No product wording; default labels are generic ("Resource", "Booking") and overridable.
- ESM output with TypeScript types; each package has its own version and changelog (Changesets).
- If something is awkward to use from `apps/console` or `apps/member`, it will be awkward for every product.

### `app-kit`

Every app starts through `app-kit`. It reads the runtime config, creates the query client, wires the JWT into the API client, initialises PostHog and Sentry with the app's name (`console` or `member`), and provides the top-level error boundary.

The query client disables `refetchOnWindowFocus` and retries, and treats a query as fresh for `staleTimeMinutes` (runtime config, default `DEFAULT_STALE_TIME_MINUTES` in `queryClient.ts`) before refetching it — screens that need fresher data after their own action call `queryClient.invalidateQueries(...)` explicitly rather than relying on a refetch-on-focus.

## UI rules

- No direct `fetch`; all server data goes through generated hooks.
- Handle errors by `code`.
- Every denial shows its reason from the rule trace.
- Every screen handles loading, empty and error states.
- Every new screen adds its tracking events in the same merge request ([analytics.md](analytics.md)).
- Every `Button` carries an icon (`Icon` from `@booking-core/ui`, leading the label) matching its action — reuse the icon already used for that action elsewhere (e.g. `Check`/`X` for approve/reject, `Plus` for add/create, `Trash` for remove/delete, `Ban` for cancel) rather than picking a new one. Exceptions: a button that is already icon-only (`IconButton`, an avatar trigger, a `size='icon*'` button), and a grid of data-selection buttons standing in for cells (calendar days, availability slots).

## Mocks

1. Edit `contracts/openapi.yaml` while building the screen.
2. Run `pnpm gen`: Orval regenerates hooks, Zod schemas and MSW mocks. Generated code is committed.
3. Add scenario handlers in `web/packages/api-client/src/scenarios/` where behaviour matters: `SLOT_TAKEN`, `BOOKING_DENIED` with reasons, slow responses. Each scenario's stateful logic lives in a plain, framework-free `*Operations.ts` module (e.g. `bookingsOperations.ts`); the MSW handlers in `*Store.ts` are a thin adapter over it, so the same logic also runs the shared mock server below.
4. Switch each feature from `mock` to `real` with the runtime `apiMode` setting and its per-feature overrides as the backend lands.

### Shared mock server, for running both apps together

Each app's own MSW mocks are per-tab and reset on reload — fine solo, but console and member then can't see each other's data. `web/mock-server` runs the same scenario operations as one real local HTTP server instead, so a resource type created in console shows up in member, a booking made in member shows up in console's approvals and bookings list, and so on. It has no state of its own beyond those operations modules — it's the in-browser mock lifted out from behind MSW, not a second implementation.

Run it alongside both apps: `pnpm --filter mock-server dev` (serves `http://localhost:4000`, reset with `POST /__reset`). Both apps' `public/config.js` point at it by default (`apiMode: 'real'`). For solo work where running a third process isn't worth it, switch an app's `public/config.js` back to `apiMode: 'mock'` — each tab gets its own throwaway MSW data again, same as before.

## Running locally

From `web/`, run `pnpm --filter console dev` and `pnpm --filter member dev` natively, side by side, against the API, worker and database in Docker Compose. Node is pinned in `web/.nvmrc`, pnpm in `web/package.json`. Images and runtime config: [operations.md](operations.md). Before that backend exists for a given feature, run `pnpm --filter mock-server dev` alongside them instead — see "Shared mock server" above.

Environment values are read at runtime from `window.__CONFIG__`, never from `import.meta.env`, so one image runs everywhere.

## Storybook

One Storybook instance (`web/storybook`) previews every component in `web/packages/*` and `web/apps/*` in isolation, without wiring it into a page or running a full app. Run it with `pnpm --filter storybook dev` (serves `http://localhost:6006`).

- A story lives next to the component it covers, as `<Component>.stories.tsx` — not in `web/storybook`, which holds only the Storybook config (`.storybook/main.ts`, `.storybook/preview.tsx`).
- `msw-storybook-addon` intercepts requests with the same scenario handlers apps use (`handlers` from `@booking-core/api-client`), reset before every story — so a story can exercise a real mutation (approve a booking, cancel it) and see it actually change, the same as in the app. Give a fixture the same id as a seeded record (see `bookingsOperations.ts`) when a story needs to act on it.
- `.storybook/preview.tsx` wraps every story in a `QueryClientProvider` and `TooltipProvider`, matching what `CoreAppProvider` does for a real app.
- Add a component's story once it's built and confirmed, not while it's still taking shape — see step 4 of ["Testing: features first, tests before commit"](#testing-features-first-tests-before-commit) below.

## Testing: features first, tests before commit

Tests written while a feature is still taking shape usually encode the wrong behaviour and get thrown away. So:

1. **Build the feature.** Don't create or edit test files yet.
2. **Hand over for verification.** Tell the developer exactly what to check: screens, loading, empty and error states, and each error code the feature handles.
3. **The developer verifies** and confirms or asks for changes. Repeat until confirmed.
4. **Add or update Storybook stories** for any new or changed component, now that it's confirmed — not earlier, while it's still taking shape (same reasoning as tests before it). See [Storybook](#storybook) above.
5. **Propose test cases before committing:** a short list, each with a name, what it covers, and its type (unit, component, end-to-end). Focus on logic and flow — state transitions, business rules, which handler fires with what data — not layout, styling or shadcn/ui itself; those change independently of the behaviour and a redesign shouldn't break the test suite. Where you can, pull decision logic (gating rules, grouping/sorting, derived state) into a plain function and test that directly, with no rendering at all. When a case genuinely has to render or interact with a component to exercise a flow — e.g. a confirmation step before a destructive action — that's fine, but say so in the proposal and add a comment in the test explaining why, so it reads as a behaviour check rather than a visual one. Prioritise user-visible behaviour, handled error codes, and edge cases found during verification. Hold end-to-end tests until the flow they cover is mostly built — a screen built alone still gets unit and component tests now.
6. **The developer approves or edits the list.**
7. **Write and run the tests** with lint and type checks. If a test fails because the feature is wrong, fix the feature. If a test expects the wrong thing, flag it. Update existing tests only for behaviour the developer confirmed, and say so.
8. **Commit the feature, its stories and its tests together.**

The developer can ask for tests first when it helps, e.g. a tricky pure function.

### What to test

| Area | Must have |
| --- | --- |
| Custom-field forms | Each field type renders and validates like the backend |
| Rule editor | Preview matches the shared rule examples |
| Errors | A clear message for each error code a screen handles |
| Key flows | Search → book → confirm; check in; cancel; approve |
| Demo | The seven demo steps, end to end with Playwright, before each rehearsal |
